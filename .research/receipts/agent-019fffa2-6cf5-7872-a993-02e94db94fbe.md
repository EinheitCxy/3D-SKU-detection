## 结论摘要

1. 短期继续采用 Python + Viser，不整体迁移到 Potree 或原生 Three.js。
2. 将当前单体 viewer 逐步拆为 scene registry、selection、camera、annotation、measurement、GUI state 等边界。
3. 使用 `/objects/<global_id>/{points,mesh,label,evidence}` 组织对象，但不要为每个点或大量证据创建节点。
4. Viser 0.2.11 已支持 click 和 rect-select；矩形选择应按 projected point mask 聚合到 global ID，并明确 visible-only / through-selection 语义。
5. 将 Pick、Rect Select、Measure、Clip 设计成互斥的显式模式，集中管理 pointer callback 生命周期。
6. 对象选择后从 AABB/包围球计算 look-at 和距离，平滑移动相机；不能只复制相机位姿。
7. 对频繁筛选预建有限数量的 chunk/LOD，优先切换 visibility，避免持续重传大点云。
8. 借鉴 Nerfstudio 的 control panel、camera control、crop 状态和交互期间低 LOD/静止后高 LOD，不引入其训练渲染栈。
9. Potree 的 octree、point budget、clipping、measurement、annotation 适合作为大规模点云参考；整体接入成本高。
10. Three.js 的 scene graph、Raycaster、SelectionBox、clipping 适合未来品牌化前端，但业务 GUI、证据 schema 和 Python 状态同步需要自行建设。
11. 颜色、label、measurement overlay 只是 evidence projection；正式证据应保留 annotation_id、global_id、frame_ids、artifact URI/digest、method/version/status/geometry 等字段。
12. 主要反模式：每次筛选重传一整个大点云、一证据一点标签、把颜色当证据状态、在 GUI callback 同步执行 Poisson meshing、默认把 rect-select 当成可见表面选择。
